# 2026-10-31 · 첫 기획서(v0.1) 작성

## 문제 맥락
`docs/concept.md`(8개 항목)를 기획서로 구체화. 핵심 불편은 같은 서버에 FileZilla·터미널로 두 번 접속하는 것과, 서버 간 이동 시 로컬 경유 수작업.

## 검토한 선택지와 결정
| 주제 | 선택지 | 결정(잠정) | 근거 |
|---|---|---|---|
| 주 프로토콜 | FTP 중심 / SFTP 중심 | SFTP 중심, FTP는 v1.x | 터미널·터널은 SSH 위에서만 성립 |
| 원격↔원격 | 로컬 스트리밍 중계 / 서버 직접 scp / FXP | 중계(MVP), 서버 직접(v1.x), FXP 제외 | 서버 설정 없이 모든 SFTP 서버에서 동작. FXP는 지원 서버 거의 없음 |
| 원격 3개 표시 | 3분할 / 탭+창별 출처 선택 | 탭+출처 선택 | 화면 폭 유지, 같은 드래그 동작으로 원격↔원격까지 해결 |
| 터널 설정 방식 | 전용 UI / 터미널 명령 | UI 먼저 | 저장·재사용·상태 표시 |
| 플랫폼 | macOS 네이티브 / Tauri·Electron | macOS 네이티브(잠정) | 기존 jena-* 앱 계열 |

## 범위 trade-off
FileZilla+Terminus 전체 재현은 하지 않음. 핵심 = "한 번 접속으로 전송+셸+터널" + "서버 간 전송". 터미널 플러그인·클라우드 저장소·팀 공유 제외.

## 미룬 것
FTP/FTPS, FileZilla 가져오기, 점프 호스트, 원격 파일 편집, 서버 직접 전송, 폴더 동기화 — MVP 가치 검증 뒤.

## 결정 대기
기획서 §12 D1~D6 (플랫폼·FTP 포함 여부·터널 방식·배포·원격 표시·판매 여부).

## v0.2 갱신 (같은 날, 작가 피드백)
- **원격↔원격 → v1.x 연기**(작가 결정). 창별 출처 선택 레이아웃 자리만 남겨 나중에 같은 드래그 동작으로 열 수 있게 함.
- **터널링 재정의**: 일반 포트 포워딩이 아니라 "터미널로 bastion 접속 → 그 경로로 내부 서버 폴더 접근". ProxyJump(direct-tcpip 위 별도 SSH 인증)를 MVP 기본으로 채택 — 종단 간 암호화·로컬 포트 불필요·bastion 인증(OTP) 재사용. bastion이 포워딩을 막은 환경용 셸 경유 방식(`ssh host -s sftp`)은 v1.x 검토(D7). 내부 서버가 진짜 FTP면 데이터 포트 문제로 별도 설계(D8). 일반 포트 포워딩 UI는 v1.x.
- **플랫폼**: mac·Windows 둘 다 네이티브. Tauri 불필요. 쟁점은 핵심 공유 여부 — N1(완전 별도) vs N2(Rust 공통 핵심 + Swift/C# UI). 어려움이 연결 관리에 몰려 있어 N2 추천, 단 스파이크로 확정. mac 먼저.
- **오픈소스 MIT**(jena-image·jena-note와 동일). → 영어 UI 필수, GPL 의존성 불가(FileZilla 코드 참조 금지).

## v0.3 갱신 (2026-11-01, 작가 피드백)
- **연결마다 SFTP/FTP/FTPS 선택 → MVP 포함**(D2 확정). 터미널은 SFTP만, FTP 연결은 bastion 터미널로 대신.
- **bastion = `ssh -p` 사용자 지정 포트 SSH.** ProxyJump는 포트 지정과 무관하게 가능(`-J user@host:port`). 포워딩 허용 여부(D7)는 여전히 미확인. 일반 bastion인지 포트 매핑 게이트웨이인지(D9) 확인 필요.
- **FileZilla 프록시 우회**: 작가 지적이 맞음 — `ssh -D` + 일반 프록시(SOCKS5)로 우회 가능. 다만 터미널·FileZilla 2단 작업이고 프록시가 전역. 이 원리(연결마다 새 통로)를 앱 내부로 가져와 **bastion 경유 FTP**를 해결: 명령·passive 데이터 연결마다 bastion 위 direct-tcpip 채널. active 모드는 경유 불가.
- 외부 프록시(SOCKS5/HTTP) 기능 자체는 v1.x, 서버별 설정으로 — bastion 내장이 MVP 용도를 덮으므로 범위 보호.

## v0.4 갱신 (2026-11-01, 작가 정정)
- bastion 접속은 `ssh -p`가 아니라 **`ssh -L 2222:<내부IP>:22 <사용자>@<bastion>`** → 로컬 2222로 내부 서버 SSH에 접속하는 방식.
- `-L` 동작 = bastion이 TCP 포워딩 허용(-J와 같은 direct-tcpip) → **D7 확정(허용), D9 확정(일반 bastion)**. ProxyJump·FTP 채널 경유 설계 그대로 유효. 대체 방식(셸 경유 B)은 우선순위 낮아짐.
- 사용 습관을 그대로 받기 위해 **ssh 명령 붙여넣기 → bastion+내부 서버 2개 자동 생성(FR-09)** 을 MVP에 추가(파서 수준, 작음).
- 작가 bastion 비밀번호가 바뀐 상황에서 착안 → **인증 실패 시 재입력·저장 갱신·실패 구간(bastion/내부) 구분(FR-03a)**.
- 공개 저장소(MIT)이므로 실제 IP·계정은 문서에 남기지 않음.

## v0.5 갱신 (2026-11-01, 작가가 초기 의도 명시)
- 초기 의도: `ssh -L`로 터미널 접속 → FileZilla로 `localhost:2222` 재접속, **두 창·매번 두 번 접속이 힘들어서 한 화면으로**. → §1.1에 원문 취지로 고정, 범위 판단 기준으로 삼음.
- 이 기준으로 보면 v0.3에서 MVP에 넣은 FTP/FTPS·3개 동시 연결은 초기 의도 해결에 필수가 아님 → **MVP 1차(의도 해결)/2차로 분리**. 빼지는 않고 순서만 뒤로(작가 요청 기능이므로).
- 이유: 1차만으로 실사용에 들어가야 고통이 빨리 끝나고, 실사용 피드백으로 2차 우선순위를 다시 매길 수 있음. 작가의 0→1 구간에서 범위가 커지면 첫 출시가 밀리는 패턴 방지.

## v0.6 갱신 (2026-11-01)
- 작가 정정: **bastion 경유는 기본이 아니다.** 직접 SFTP 접속이 기본, 경유는 서버별 체크(기본 꺼짐). v0.5에서 1차 범위를 bastion 중심으로 서술해 기본처럼 읽힌 것을 바로잡음(FR-02a).
- 작가 질문으로 russh vs libssh2 비교를 §11.1에 추가. 결론 보류 — 스파이크 실측으로 D1b와 함께 확정.

## v0.7 갱신 (2026-11-01) — SSH 라이브러리 결정
- 작가 결정: **russh**. 따라서 핵심 구조도 N2(Rust 공통 핵심 + Swift/C# 화면) 확정.
- 근거: 한 연결 다중 채널·ProxyJump·경유 FTP가 russh의 비동기·스트림 채널 구조에 맞음.
- 위험 보험: libssh2로 되돌릴 기준 4개(SFTP scp 대비 70% 미만 / OTP 불가 / ProxyJump 불가 / 실제 서버 접속 불가) 명시. 버전 고정·transport 모듈 격리.
- 스파이크는 비교 실험이 아니라 russh 단일 검증으로 축소 → 시간 절약.
