## 1. 목적

### 1.1 출발점 (작가의 초기 의도)

> 지금까지는 터미널에서 `ssh -L 2222:<내부IP>:22 <사용자>@<bastion>`으로 먼저 접속한 뒤, FileZilla에서 `localhost:2222`로 다시 접속해서 작업했다.
> **창 2개를 띄워 매번 두 번 접속하는 게 번거롭고 힘들어서, 이걸 한 화면에서 되게 만드는 것**이 이 프로젝트의 시작이다.

이 문장이 모든 범위 판단의 기준이다. 어떤 기능을 넣을지 망설여지면 **"이게 저 두 창·두 번 접속을 한 화면·한 번으로 줄이는 데 필요한가?"** 를 먼저 묻는다.

### 1.2 목적

- **한 번 접속, 한 화면**: 접속 동작 한 번으로 같은 창에 그 서버의 **파일 창 + 터미널**이 함께 열린다.
- **기본은 직접 SFTP 접속.** bastion 경유는 **필요한 서버에만 켜는 선택 사항**이다(기본값 "경유 없음"). 직접 접속하는 서버가 더 많고, bastion은 그중 일부 서버의 접속 경로일 뿐이다.
- bastion 경유를 켠 서버는 터미널을 먼저 띄워 두거나, 로컬 포트를 맞추거나, FileZilla에 다시 접속할 필요 없이 똑같이 한 번 접속으로 열린다.
- 그 위에 FileZilla 수준의 전송 편의(대기열·이어받기·덮어쓰기 규칙)와 서버 관리를 갖춘다.

## 2. 문제 정의

| 지금의 불편 | 원인 | 결과 |
|---|---|---|
| 같은 서버에 FileZilla와 터미널로 따로 접속 | 전송 도구와 셸 도구가 분리됨 | 접속 정보 이중 관리, 창 전환 비용 |
| bastion 뒤 내부 서버에 파일 전송이 번거로움 | **작가의 현재 방식**: 터미널에서 `ssh -L 2222:<내부IP>:22 <사용자>@<bastion>`으로 로컬 2222 포트를 내부 서버 22번에 연결해 두고, 파일 전송 도구는 `localhost:2222`로 접속. (FileZilla에선 `ssh -D` + "일반 프록시" SOCKS 방식도 가능.) 어느 쪽이든 **터미널과 FileZilla에서 따로 맞추는 2단 작업**이다 | 터미널을 먼저 열어 두지 않으면 FileZilla가 안 붙음, 내부 서버마다 로컬 포트 번호를 외워 맞춰야 함(2222·2223…), 비밀번호가 바뀌면 터미널·FileZilla 두 곳에서 각각 실패, 프록시 방식은 설정이 전역이라 직접 접속 서버와 섞일 때 껐다 켜야 함, 터널이 끊기면 파일 창도 죽는데 이유가 안 보임 |
| 서버 목록이 도구마다 흩어짐 | FileZilla 사이트 관리자, `~/.ssh/config`, 터미널 앱 프로필 | 한 곳을 고치면 다른 곳이 낡음 |

**Job to be done**: "bastion을 거쳐 내부 서버에 들어가서, 셸로 상황을 보고, 같은 자리에서 파일을 올리고 내린다 — 한 번의 접속으로."

## 3. 대상 사용자 · 사용 장면

- **1차 사용자: 제롬(본인)** — bastion 뒤 고객사 서버, RunPod Pod, 개인 VPS를 오가는 개발자.
- 2차: 오픈소스 사용자(GitHub 공개, jena-image·jena-note와 같은 방식). 같은 불편을 가진 개발자·운영자.

대표 장면
1. **bastion 경유**: 터미널에서 bastion에 접속(OTP 입력) → 내부 서버 `app-01`의 `/var/www`를 파일 창에서 열고 배포 파일 업로드 → 같은 경로의 터미널에서 `systemctl restart`.
2. 같은 bastion을 통해 `app-01`, `db-01` 두 내부 서버를 동시에 열기(bastion 인증은 한 번).
3. RunPod Pod에 직접 접속 → 결과물 내려받으면서 아래 터미널로 `nvidia-smi` 확인.

## 4. 가정 (Assumptions)

> 아래가 틀리면 기획이 바뀐다. 개발 착수 전 각각 확인할 것.

| # | 가정 | 틀렸을 때 영향 | 확인 방법 |
|---|---|---|---|
| A1 | 연결마다 **SFTP / FTP / FTPS를 고른다**. 터미널은 SSH 위에서만 성립하므로 SFTP 연결에만 붙는다. bastion 뒤의 FTP 서버는 **passive 모드**를 지원한다 | 내부 FTP가 active 모드만 되면 bastion 경유 불가(데이터 연결 방향이 반대라서) | 내부 FTP 서버 설정 확인 |
| A2 | ✅ **확인됨(2026-11-01)** — 작가의 bastion은 TCP 포워딩을 허용한다. 근거: `ssh -L 2222:<내부IP>:22 …` 접속이 동작했음. `-L`과 `-J`(ProxyJump)는 같은 SSH 기능(direct-tcpip 채널)을 쓰므로 §8.3 A·C 방식 모두 가능 | — | 완료 |
| A3 | 경유는 **1단계(bastion 하나)** 면 충분하다 | 2단 이상이면 경유 체인 UI 필요(구조는 처음부터 체인으로 설계) | 사용 환경 확인 |
| A4 | 동시 원격 연결은 **최대 3개**로 충분하다. bastion은 개수에 세지 않는다 | 더 필요하면 상한만 조정 | 사용 4주 관찰 |
| A5 | 터미널 품질은 "일상 셸 작업(vim·htop·tmux)이 깨지지 않는 수준". Terminus(Tabby) 플러그인·테마 생태계는 필요 없다 | 고급 터미널 기능 요구 시 범위 급증 | MVP 사용 후 판단 |

## 6. 범위

### 6.1 포함 (MVP — v1.0)

MVP 안에서도 **초기 의도를 푸는 부분을 먼저** 끝내고 실사용에 들어간다. 1차만으로 "ssh -L + FileZilla 두 창"을 버릴 수 있어야 한다.

**MVP 1차 — 초기 의도 해결 (먼저 완성 → 바로 실사용)**
- SFTP 접속(비밀번호 / 키 파일 / ssh-agent / keyboard-interactive(OTP)), 호스트 키 검증
- **한 번의 SSH 접속에서 SFTP + 터미널을 함께 사용**(채널 공유)
- **bastion 경유 접속(선택)** — 서버별로 필요할 때만 켬, 기본은 꺼짐(직접 접속). 켜면 ProxyJump 방식, bastion 인증 1회, 로컬 포트 없음
- **터미널 → 파일 창 연결**: bastion 터미널에서 내부 서버를 파일 창으로 바로 열기
- **ssh 명령 붙여넣기로 서버 만들기**(FR-09) — 지금 쓰는 `ssh -L` 명령을 그대로 옮겨 오기
- 비밀번호 변경 시 재입력·저장 갱신(FR-03a)
- 로컬·원격 2분할 탐색기, 드래그 앤 드롭 전송, 전송 대기열, 이어받기
- 하단 터미널(연결별 탭)
- 서버 관리(저장·편집·경유 서버 지정, 비밀번호는 OS 자격 증명 저장소)
- 상태 로그, 전송 진행 표시

**MVP 2차 — 1차 실사용 중에 이어서**
- **연결마다 프로토콜 선택: SFTP / FTP / FTPS** + FTP·FTPS 접속(passive 기본, FTPS 명시적·암시적 TLS)
- bastion 경유 FTP·FTPS(§8.3 C)
- 원격 최대 3개 동시 연결(오른쪽 창 탭) — 1차는 1개(+bastion)로도 초기 의도는 충족
- 서버 관리 그룹·복제, `~/.ssh/config` 가져오기(`ProxyJump` 포함)

### 6.2 다음 (v1.x)

- **원격 ↔ 원격 전송**(작가 결정으로 연기) — 레이아웃은 미리 대비해 둠(§7.1 출처 선택)
- 포트 포워딩(-L/-R/-D) 관리 UI
- **외부 프록시(SOCKS5 / HTTP CONNECT)** — FileZilla "일반 프록시"와 같은 기능. 회사 프록시 뒤 환경이나 이미 열어 둔 `ssh -D`를 쓰려는 경우용. 단 FileZilla와 달리 **서버별 설정**(전역 아님). bastion 경유가 내장되어 있어 MVP에선 필수가 아님
- FileZilla `sitemanager.xml` 가져오기
- 경유 2단 이상(체인)
- 원격 파일 바로 편집(로컬 편집기로 열고 저장 시 자동 업로드)
- 폴더 비교·동기화

### 6.3 제외 (하지 않음)

- 클라우드 저장소(S3·Google Drive 등)
- 터미널 플러그인·테마 마켓
- 팀 공유·동기화 서버
- FXP(FTP 서버 간 직접 전송)

## 7. 화면 구성

### 7.1 메인 레이아웃 (concept 3번 그대로)

```
┌───────────────────────────────────────────────────────────────────┐
│ [메뉴] 파일 · 서버 관리 · 전송 · 보기                                 │
├───────────────────────────────────────────────────────────────────┤
│ 빠른 접속: [SFTP▼] 호스트[    ] 사용자[   ] 비밀번호[   ] 포트[22]     │
│           ☐ 경유(터널링) [bastion ▼ 선택] [접속] [최근▼]              │
├─────────────────────────────┬─────────────────────────────────────┤
│ 상태 로그                      │ 전송 상태                              │
│ 22:31 [bastion] 인증 성공(OTP)  │ ▶ app.tar  로컬→A  62%  48MB/s  0:21  │
│ 22:31 [A] bastion 경유 접속      │ ⏸ log/*    A→로컬  대기 12개           │
│ 22:32 [A] /var/www 목록         │ ✓ conf.yml 로컬→A  완료                │
├─────────────────────────────┬─────────────────────────────────────┤
│ 로컬                          │ [A: app-01 ⇢bastion] [B] [C]         │
│ 경로: ~/Downloads             │ 경로: /var/www                        │
│ ─ 폴더 트리 ─                   │ ─ 폴더 트리 ─                          │
│ ─ 파일 목록 ─                   │ ─ 파일 목록 ─                          │
├─────────────────────────────┴─────────────────────────────────────┤
│ 터미널  [bastion] [A: app-01] [B: db-01] [+]                       │
│ ubuntu@app-01:/var/www$ _                     [📁 파일 창에서 열기]   │
└───────────────────────────────────────────────────────────────────┘
```

- 프로토콜을 바꾸면 포트 기본값이 따라 바뀜(SFTP 22 / FTP 21 / FTPS 암시적 990). 사용자가 포트를 직접 고쳤으면 덮어쓰지 않음
- 경유 접속한 연결은 탭에 `⇢bastion` 표시, 원격 탭에 프로토콜 배지(`SFTP`/`FTP`/`FTPS`) — 지금 이 서버가 어떤 길·어떤 방식으로 붙어 있는지 늘 보이게
- 터미널 탭과 원격 탭은 **연결 단위로 색을 맞춘다**(A=파랑 등)
- 좌우 창 머리에 **출처 선택**(로컬 / A / B / C) 자리를 만들어 둔다. MVP에서는 왼쪽=로컬 고정, v1.x에서 열어주면 원격↔원격이 같은 드래그 동작으로 풀린다(설계만 미리)
- 영역 경계 크기 조절, 상태 로그·전송 상태·터미널 접기 가능
- 연결 4개째 시도 시: "최대 3개까지 연결할 수 있어요. 하나를 끊고 다시 시도하세요." + 연결 목록

## 8. 기능 요구사항

### 8.1 연결 · 서버 관리 (concept 4)

- FR-01 빠른 접속 바: **프로토콜**·호스트·사용자·비밀번호·포트·**경유 서버** 입력 후 접속. 최근 접속 10개. 호스트 칸에 `sftp://`·`ftp://`·`ftps://`를 붙여 넣으면 프로토콜이 자동 선택됨.
- FR-02 서버 관리자: 이름·그룹·**프로토콜**·호스트·포트·사용자·인증 방식·기본 원격/로컬 경로·색상·**경유 서버**.
- FR-02a **경유는 선택 사항**: 서버 편집 화면의 "bastion 경유" 체크는 **기본 꺼짐**. 끄면 직접 접속(대부분의 서버), 켤 때만 경유 서버(저장된 SSH 서버 중 선택) 칸이 나타난다. 빠른 접속 바도 같다 — 체크하지 않으면 경유 칸은 비활성.
  - 하나의 서버는 **직접 서버로도, 다른 서버의 bastion으로도** 쓰일 수 있다(예: bastion 자체에 직접 SFTP 접속해서 파일 보기).
  - FR-09 명령 붙여넣기: `ssh <사용자>@<호스트>`처럼 `-L`/`-J`가 없으면 **직접 접속 서버 하나**만 만든다.
- FR-07 **프로토콜별 동작**

  | 항목 | SFTP | FTP | FTPS |
  |---|---|---|---|
  | 기본 포트 | 22 | 21 | 21(명시적) / 990(암시적) |
  | 인증 | 비밀번호·키·agent·OTP | 비밀번호·익명 | 비밀번호·익명 |
  | 암호화 | SSH | **없음** — 접속 전 "비밀번호가 암호화되지 않고 전송돼요" 1회 경고(서버별 "다시 묻지 않기") | TLS. 인증서 처음 볼 때·바뀌었을 때 확인 창 |
  | 전송 모드 | — | passive 기본 / active 선택(직접 접속일 때만) | 동일 |
  | 터미널 | ✅ 같은 세션 | ❌ | ❌ |
  | bastion 경유 | ✅ (§8.3 A) | ✅ passive만 (§8.3 C) | ✅ passive만 |
  | 권한 변경(chmod) | ✅ | 서버가 `SITE CHMOD` 지원 시 | 동일 |
  | 이어받기 | ✅ | `REST` 지원 시 | 동일 |
  | 문자 인코딩 | UTF-8 | 자동(UTF-8) / 수동(EUC-KR 등) — 옛 서버 한글 파일명 대비 | 동일 |

- FR-08 bastion 서버 자체는 항상 **SSH**(프로토콜 선택 없음), 포트는 자유 지정(기본 22).
- FR-09 **ssh 명령 붙여넣기로 서버 만들기**(MVP, 작음): 빠른 접속 바나 서버 관리자에 평소 쓰던 명령을 붙여 넣으면 해석해 서버를 만든다.
  - `ssh -L 2222:<내부IP>:22 <사용자>@<bastion>` → bastion 서버(`<사용자>@<bastion>:22`) + 그 bastion을 경유하는 내부 서버(`<내부IP>:22`, SFTP) **두 개를 한 번에** 생성. 로컬 포트 번호(2222)는 더 이상 필요 없으므로 버린다(안내 문장으로 알려줌)
  - `ssh -J`·`-p`·`-i`(키 파일)·`user@host`도 해석. 모르는 옵션은 무시하고 목록으로 보여줌
  - 비밀번호는 붙여 넣은 명령에 없으므로 첫 접속 때 묻는다
- FR-03a **비밀번호가 바뀌었을 때**: 인증 실패 시 다시 입력받고 "저장된 비밀번호를 바꿀까요?"로 키체인·자격 증명 저장소 갱신. bastion과 내부 서버 중 **어느 쪽 인증이 실패했는지 구분**해 표시.
- FR-03b **비밀번호 만료**: 인증은 통과했는데 서버가 비밀번호 변경을 요구하는 경우(OpenSSH/PAM — TTY 없는 SFTP 세션은 즉시 종료됨). 서버 메시지(`Your password has expired`)를 감지해 "이 계정의 비밀번호가 만료됐어요"로 알리고, **[터미널에서 변경]** 버튼으로 같은 경로(bastion 경유 포함)의 PTY 터미널 탭을 열어 변경하게 한다. 변경 후 저장된 비밀번호 갱신(FR-03a)으로 이어짐. (2026-11-01 실제 서버 스파이크에서 발견)
- FR-03 비밀번호·키 암호는 **OS 자격 증명 저장소에만**(macOS 키체인 / Windows 자격 증명 관리자). 설정 파일 평문 저장 금지. OTP는 저장하지 않음.
- FR-04 호스트 키: 첫 접속 시 지문 확인, 키가 바뀌면 **접속 차단 + 경고**. bastion과 내부 서버를 각각 검증. `~/.ssh/known_hosts` 호환.
- FR-05 `~/.ssh/config` 가져오기(Host·HostName·User·Port·IdentityFile·**ProxyJump**).
- FR-06 동시 연결 최대 3개(bastion은 제외). 상한은 설정값 하나로 관리.

### 8.2 파일 탐색 · 전송 (concept 1, 3, 8-FileZilla 참조)

- FR-10 좌우 창: 폴더 트리 + 파일 목록(이름·크기·수정일·권한·소유자), 정렬, 경로 직접 입력, 뒤로/앞으로, 숨김 파일 토글.
- FR-11 전송: 드래그 앤 드롭, 우클릭 메뉴, 단축키. 폴더 재귀 전송.
- FR-12 전송 대기열: 동시 전송 수(기본 3), 일시정지·재개·취소·우선순위.
- FR-13 이어받기: 끊긴 전송은 받은 지점부터 재개.
- FR-14 덮어쓰기 규칙(S-05), "모두 적용".
- FR-15 원격 파일 작업: 새 폴더, 이름 바꾸기, 삭제(확인 창), 권한 변경.
- FR-16 실패 전송은 원인과 함께 대기열에 남기고, 앱 재시작 후에도 복원.

### 8.3 bastion 경유 접속 (concept 5 — "터미널을 통한 터널링")

**작가 의도**: 터미널에서 bastion에 SSH로 들어가고, 그 bastion을 통해 내부 서버의 폴더에 파일 창으로 접근한다.

**작가의 현재 방식과 바뀌는 점**

| | 지금 (`ssh -L`) | jena-file |
|---|---|---|
| 준비 | 터미널에서 `ssh -L 2222:<내부IP>:22 …` 실행 후 창을 열어 둠 | 서버 목록에서 내부 서버 더블클릭 |
| 파일 전송 | FileZilla에서 `localhost:2222`로 별도 접속 | 같은 화면 파일 창에 바로 열림 |
| 내부 서버 셸 | bastion 셸에서 다시 `ssh` | 내부 서버 터미널 탭이 바로 열림 |
| 로컬 포트 | 2222를 열어 둠(서버마다 번호 관리) | 열지 않음 |
| 내부 서버 여러 대 | `-L`을 서버마다 추가 | bastion 하나에 여러 대 |

원리는 같다 — `-L`이 bastion에게 "내부IP:22로 통로를 열어 줘"라고 요청하는 그 기능을, 로컬 포트를 거치지 않고 앱 안에서 직접 쓴다.

**FileZilla와의 차이**: FileZilla도 터미널에서 `ssh -D`로 SOCKS 프록시를 띄우고 "일반 프록시"를 지정하면 우회는 된다. jena-file은 이 두 단계를 **앱 안에서 한 번에** 한다 — 로컬 포트를 열지 않고, 서버마다 경유 여부가 저장되며, bastion 상태가 파일 창·터미널과 같이 보인다.

- FR-20 **A. SFTP 내부 서버 — ProxyJump 방식(MVP 기본)**
  1. bastion에 SSH 접속·인증(비밀번호/키/OTP) → bastion 터미널 탭이 열림
  2. bastion 세션 위에 내부 서버로 가는 통로(direct-tcpip 채널)를 열고, 그 통로 위에서 내부 서버와 **별도의 SSH 인증**을 맺음
  3. 내부 서버 세션에서 SFTP(파일 창) + 셸(터미널 탭)을 함께 사용
  - 장점: `ssh -J`와 같은 표준 방식, 내부 서버 인증 정보가 bastion에 노출되지 않음(종단 간 암호화), 로컬 포트를 열지 않음
  - 전제: bastion이 TCP 포워딩을 허용해야 함 — 작가 환경은 `-L`이 동작했으므로 충족(가정 A2)
- FR-21 **터미널에서 시작하기**: bastion 터미널 탭에서 [📁 내부 서버 열기] → 호스트·포트·사용자 입력(또는 저장된 서버 선택) → 이미 인증된 bastion 세션을 재사용해 FR-20 2~3단계 진행. **bastion 재인증(OTP) 없음**.
- FR-22 같은 bastion 세션 위에 내부 서버 여러 대(동시 연결 상한 안에서).
- FR-23 연결 상태에 경로 표시(`로컬 → bastion → app-01`), 실패 시 어느 구간인지 구분해 알림.
- FR-24 bastion 세션이 끊기면 그 위 연결 전부 일시정지 → bastion 재연결(필요 시 OTP 재요청) 후 순서대로 복구.
- FR-25 **B. bastion 셸 경유 방식(대체, v1.x 검토)** — bastion이 TCP 포워딩을 막은 환경용. bastion에서 `ssh app-01 -s sftp` 같은 명령을 실행해 그 입출력 위로 SFTP를 주고받는 방식. bastion에 내부 서버용 키가 있거나 에이전트 포워딩이 필요해 보안 검토 후 결정.
- FR-26 **C. FTP·FTPS 내부 서버 — bastion 채널 경유(MVP)**
  - FTP는 명령 연결(21번) 외에 파일·목록마다 **데이터 연결을 새로 연다**. 그래서 `ssh -L` 포트 하나로는 동작하지 않는다(FileZilla가 SOCKS 프록시 방식을 쓰는 이유).
  - jena-file은 SOCKS와 같은 원리를 앱 안에서 한다: 명령 연결도, passive 응답(`PASV`/`EPSV`)으로 받은 데이터 포트도 **각각 bastion 세션 위에 새 통로(direct-tcpip 채널)** 를 열어 연결한다. 로컬 포트는 열지 않는다.
  - passive 응답의 주소가 내부 IP여도 bastion이 닿을 수 있으면 그대로 사용. 응답 주소가 엉뚱하면(NAT 뒤 서버) 명령 연결의 호스트로 대체.
  - **active 모드는 bastion 경유에서 지원하지 않음**(서버가 거꾸로 우리 쪽에 연결해야 해서 불가). 선택 시 "bastion 경유에서는 passive만 쓸 수 있어요" 안내.
  - FTPS는 이 통로 위에서 TLS를 맺으므로 종단 간 암호화 유지.
  - 터미널: FTP 내부 서버엔 셸이 없으므로 **bastion 터미널 탭**을 함께 띄움(작가 사용 흐름 — bastion 셸에서 상황 확인 + 파일 창은 내부 FTP).

### 8.4 터미널 (concept 2, 8-Terminus 참조)

- FR-30 SFTP 연결마다 터미널 탭. 같은 SSH 세션 공유(다시 로그인하지 않음). bastion 자체도 탭으로 열 수 있음. FTP·FTPS 연결엔 터미널 탭이 생기지 않음(bastion 경유면 bastion 탭으로 대신).
- FR-31 xterm-256color, 트루컬러, 한글 입력·출력(IME 조합 중 표시 포함), vim·htop·tmux 정상 동작.
- FR-32 복사·붙여넣기, 스크롤백(기본 1만 줄), 찾기, 글꼴·크기 설정.
- FR-33 파일 창 ↔ 터미널 연동: 원격 창에서 "여기서 터미널 열기" → 해당 경로로 `cd`. 파일을 터미널로 끌어다 놓으면 경로가 입력됨.
- FR-34 로컬 셸 탭(연결 없이).

### 8.5 로그

- FR-50 상태 로그: 시각 · 연결(bastion/A/B/C) · 내용. 연결별 필터, 오류만 보기, 복사.
- FR-51 비밀번호·키·OTP는 로그에 절대 남기지 않음.

## 10. 수용 기준 (주요 시나리오)

**AC-1 한 번 접속으로 전송 + 셸**
- Given 직접 접속 서버 A가 저장되어 있을 때
- When 서버 관리자에서 A를 더블클릭하면
- Then 3초 안에 원격 목록과 셸 프롬프트가 뜨고, 인증은 한 번만 묻는다.
- 왜: 두 번 접속하는 불편이 이 제품의 출발점이므로.

**AC-2 bastion 경유 — 터미널에서 시작**
- Given 터미널에서 bastion에 접속(OTP 입력)한 상태
- When bastion 탭의 [📁 내부 서버 열기]에서 `app-01`을 고르면
- Then OTP를 다시 묻지 않고, 파일 창에 `app-01`의 홈 폴더가, 터미널에 `app-01` 셸 탭이 열린다. 탭에 `⇢bastion`이 표시된다.
- 왜: "터미널로 bastion에 들어간 그 길로 내부 폴더에 접근"이 작가 의도이므로.

**AC-3 bastion 인증 재사용**
- Given AC-2 상태 When `db-01`을 추가로 열면 Then OTP 재입력 없이 열리고, 연결 수는 2(bastion 제외)다.

**AC-4 구간별 실패 안내**
- Given bastion은 연결됐고 `app-01:22`가 막혀 있을 때
- When 내부 서버 열기를 하면
- Then "bastion까지는 연결됐지만 app-01:22에 닿지 못했어요"처럼 실패 구간을 알려주고, bastion 연결은 그대로 유지된다.
- Error: bastion이 TCP 포워딩을 막았으면 "이 bastion은 경유 접속(TCP 포워딩)을 허용하지 않아요"로 구분.

**AC-5 끊김 후 이어받기**
- Given bastion 경유 2GB 다운로드 50% 시점
- When 네트워크를 30초 끊었다 복구하면
- Then bastion → 내부 서버 순으로 재연결(OTP가 필요하면 요청) 후 50%부터 이어서 받고, 최종 파일 해시가 원본과 같다.

**AC-6 호스트 키 바뀜**
- Given 내부 서버의 호스트 키가 known_hosts와 다를 때 When 경유 접속하면 Then 그 구간에서 멈추고 경고 창을 띄운다. 허용 전엔 어떤 데이터도 보내지 않는다.

**AC-7 연결 상한**
- Given 3개 연결 중 When 4번째 접속 Then 안내 문장과 함께 거절, 기존 연결 영향 없음.

**AC-8 프로토콜 선택**
- Given 서버 관리자에서 새 서버를 만들 때
- When 프로토콜을 SFTP → FTP로 바꾸면
- Then 포트가 22 → 21로 바뀌고(직접 고친 포트는 유지), 인증 방식에서 키·agent 항목이 사라지며, 저장 후 접속하면 터미널 탭 없이 파일 창만 열린다.
- FTP(암호화 없음)로 처음 접속할 때 경고를 한 번 보여준다.
- 왜: 같은 화면에서 SFTP·FTP 서버를 섞어 관리하되, 무엇이 되고 안 되는지 헷갈리지 않게.

**AC-9 bastion 경유 FTP**
- Given bastion에 접속된 상태, 내부 FTP 서버 `ftp-01:21`이 저장됨(passive)
- When `ftp-01`을 열고 100MB 파일을 내려받으면
- Then 로컬 포트를 열지 않고 목록 조회·전송이 성공하며, 터미널엔 bastion 탭이 함께 보인다.
- Error: active 모드로 저장돼 있으면 "bastion 경유에서는 passive만 쓸 수 있어요"를 보여주고 passive로 전환을 제안.

## 11. 기술 방향 — macOS · Windows 둘 다 네이티브

**Windows까지 간다고 Tauri로 가야 하는 건 아니다.** 두 OS 모두 네이티브로 가면 화면(UI)은 OS마다 따로 짜야 한다. 남는 질문은 **"UI 아래 핵심(SSH·SFTP·전송 대기열·서버 목록)을 한 번만 짤 것인가, 두 번 짤 것인가"** 다.

| 안 | 구조 | 장점 | 단점 |
|---|---|---|---|
| **N1. 완전 별도** | mac=Swift/AppKit, Windows=C#/WinUI 3, 핵심도 각각 | 각 OS에 가장 자연스러움, 빌드 단순 | 핵심 로직(재연결·이어받기·bastion 복구 같은 어려운 부분)을 **두 번 짜고 두 번 고침** |
| **N2. 공통 핵심 + 네이티브 UI** | 핵심=Rust 라이브러리(SSH/SFTP/대기열/설정), UI=Swift(mac)·C#(Windows)가 FFI로 호출 | 어려운 부분은 한 번, 버그 수정도 한 번. UI만 OS별 | Rust·FFI 경계 학습·빌드 구성 비용, 초기 속도 느림 |
| (참고) T. Tauri | 핵심=Rust, UI=웹(한 벌) | 코드 한 벌, 터미널은 xterm.js(Tabby와 같은 계열)로 안정적 | 네이티브 UI 아님 — 작가 의도와 다름 |

**결정(2026-11-01 작가): N2 — Rust 공통 핵심(russh) + 네이티브 화면, macOS 먼저.**
- 이 앱의 어려움은 화면이 아니라 **연결 관리(bastion 경유·재연결·이어받기)** 에 몰려 있다. 그걸 두 번 짜면 두 번 틀린다.
- 0단계 스파이크는 **russh 하나로** 진행해 "이대로 가도 되는지"를 확인한다(두 라이브러리 비교 아님). 아래 **되돌림 기준**에 걸릴 때만 libssh2를 다시 검토한다.

### 11.1 SSH 라이브러리 비교 — russh(Rust) vs libssh2(C)

> 각 라이브러리의 최신 지원 범위는 0단계 스파이크에서 공식 문서·실측으로 다시 확인한다. 아래는 착수 전 판단용.

| | libssh2 | russh |
|---|---|---|
| 언어 · 역사 | C, 2000년대부터. curl·libgit2 등이 쓰는 검증된 라이브러리 | 순수 Rust, 비교적 젊음(thrussh에서 갈라짐) |
| 라이선스 | BSD-3 (MIT 호환) | Apache-2.0 (MIT 호환) |
| SFTP | 내장 | 별도 크레이트(russh-sftp) |
| 동작 모델 | 동기 함수 + 논블로킹 모드. **세션 하나를 여러 스레드가 동시에 못 씀** → SFTP·셸 여러 개·터널을 한 세션에 얹으려면 직접 이벤트 루프·직렬화를 짜야 함 | 비동기(tokio). 채널마다 독립 작업으로 돌리기 자연스러움 |
| bastion 경유(ProxyJump) | 내장 없음. 경유 채널 위에 두 번째 세션을 올리려면 소켓 대신 송수신 콜백을 끼워야 해서 손이 많이 감 | 채널이 스트림이라 **그 위에 두 번째 SSH 세션을 바로 올릴 수 있음** — 경유가 자연스러움 |
| FTP 데이터를 SSH 채널로 | 채널을 소켓처럼 감싸는 어댑터 직접 구현 | 채널이 스트림이라 비교적 쉬움(FTP 라이브러리가 임의 스트림을 받는지는 별도 확인) |
| 암호 백엔드 | OpenSSL / mbedTLS / Windows CNG 중 선택 → OS별 빌드 구성 필요 | ~~순수 Rust 암호 → 빌드가 단순~~ **정정(2026-11-01)**: 기본은 aws-lc-rs(C·어셈블리), 대안 `ring`도 C 포함. macOS는 문제없이 빌드됨, Windows 빌드 도구는 착수 전 확인 |
| 메모리 안전 | C — 과거 보안 취약점(CVE) 이력 있음 | Rust — 메모리 오류 계열이 구조적으로 적음 |
| 성숙도 · 위험 | 오래 쓰여 구석 동작(오래된 서버·특이 인증)이 다듬어짐. 대용량 SFTP 속도는 OpenSSH보다 느리다는 평이 있어 실측 필요 | 버전 사이 API 변경이 잦은 편, 특이 서버 호환성은 실측 필요 |
| 어울리는 구조 | **N1**(Swift·C#이 C 라이브러리를 직접 호출) | **N2**(Rust 공통 핵심 + Swift·C# 화면) |

**결정: russh** (2026-11-01 작가). 이 앱의 어려운 부분(한 연결에 SFTP·셸 여러 개, bastion 경유, 경유 FTP)이 russh 구조에 맞기 때문. libssh2의 강점(성숙도)은 아래 되돌림 기준으로 보험을 건다.

**되돌림 기준** — 스파이크에서 아래 중 하나라도 해결 못 하면 libssh2 재검토:
1. 1GB SFTP 전송이 같은 망 `scp` 대비 **70% 미만**(목표 90%, 튜닝 여지 감안한 하한)
2. keyboard-interactive(OTP) 인증 불가
3. 경유 채널 위 두 번째 SSH 세션(ProxyJump) 불가
4. 작가가 실제 쓰는 서버(bastion·내부 서버·RunPod) 중 하나라도 접속 불가(알고리즘 호환성)

**스파이크 결과(2026-11-01)**: 되돌림 기준 1~3 통과, 4는 실제 서버에서 접속·인증·경유·호스트 키까지 통과(SFTP는 내부 계정 비밀번호 만료로 보류 — 라이브러리 문제 아님). 지연 회선에선 SFTP 기본값이 느려(20ms에서 scp의 23%) **동시 요청 64 · 쓰기 128KB · 채널 창 32MB**를 앱 기본값으로 확정 → scp의 103~217%. 상세 `docs/spike/2026-11-01-russh.md`.

**버전 고정**: russh는 버전 사이 API 변경이 잦으므로 `Cargo.lock` 커밋 + 업그레이드는 별도 작업으로만. russh 사용 코드는 핵심 내부의 `transport` 모듈 한 곳에 가둬, API가 바뀌어도 고칠 곳을 한정한다.

**핵심 구조**: 연결 1개 = SSH 세션 1개. 그 위에 SFTP 채널·셸 채널(탭 수만큼)이 얹힌다. 경유 연결은 "부모 세션(bastion) 위의 자식 세션"으로 표현해 체인(2단 이상)으로 확장 가능하게 한다. 파일 창·터미널은 모두 연결 객체를 참조만 한다.
