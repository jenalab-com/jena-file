# 0단계 스파이크 결과 — russh (2026-11-01)

> 기획서 §11.1 되돌림 기준 · §13 0단계. 환경: M-series Mac(arm64), Docker Desktop, 시험 서버 = Debian bookworm OpenSSH 2대(bastion: 127.0.0.1:2201, app01: 내부망 전용). russh 0.65.0 · russh-sftp 3.0.1 · Rust 1.99.1. 코드 `spike/russh-spike`.

## 결론

**russh로 계속 간다.** 되돌림 기준 1~3 통과. 4번(실제 서버)은 **접속·인증·bastion 경유·호스트 키 대조까지 통과**, SFTP는 서버 쪽 계정 상태(비밀번호 만료) 때문에 막혀 있어 비밀번호 변경 후 재확인한다 — russh 문제 아님(아래 '실제 서버 시험').

단, **SFTP 기본 설정 그대로는 지연이 있는 회선에서 느리다**(아래 표 ①). 동시 요청 수·요청 크기·채널 창 크기를 키우면 `scp`보다 빨라진다. 앱의 기본값으로 반드시 반영한다.

| 항목 | 결과 | 비고 |

| 비밀번호 인증 / 틀린 비밀번호 | ✅ / ✅ | 실패를 구분해 받음(FR-03a 재입력 흐름 가능) |
| keyboard-interactive(OTP와 같은 방식) | ✅ | 서버 질문(`Password:`, echo 여부)을 그대로 받아 응답 — OTP 질문도 같은 경로 |

## 처리량 (1 GiB, MiB/s)

| 조건 | scp 업 | scp 다운 | russh 업 | russh 다운 | russh/scp |
|---|---|---|---|---|---|
| 직접 · 지연 없음 · 기본 설정 | 93.3 | 100.0 | 123.9 | 131.0 | 133% / 131% |
| 경유 · 지연 없음 · 기본 설정 | 93.0 | 94.0 | 99.3 | 132.2 | 107% / 141% |
| ① 직접 · **20ms 지연 · 기본 설정** | 75.3 | 77.1 | **17.1** | **40.7** | **23% / 53% ❌** |
| 직접 · 20ms · 동시 64 / 32KB / 창 16MB | 〃 | 〃 | 66.5 | 86.1 | 88% / 112% |
| 직접 · 20ms · 동시 32 / 128KB / 창 16MB | 〃 | 〃 | 73.6 | 91.7 | 98% / 119% |
| ② 직접 · 20ms · **동시 64 / 128KB / 창 32MB** | 〃 | 〃 | **77.2** | **98.1** | **103% / 127% ✅** |
| ③ 경유 · 20ms · 동시 64 / 128KB / 창 32MB | 27.7 | 37.7 | 32.7 | 81.7 | 118% / 217% ✅ |

- 원인(①): russh-sftp 기본값은 32KB 요청 16개(512KB)만 동시에 보낸다. 왕복 20ms면 이론상 약 25MB/s가 상한 — 실측과 맞음. 라이브러리 한계가 아니라 **기본값 문제**.
- **앱 기본값 결정**: SFTP 동시 요청 64, 쓰기 요청 128KB, SSH 채널 창 32MB(②). 설정 화면엔 노출하지 않고 내부 값으로.
- 지연은 bastion 컨테이너에 `tc netem delay 20ms`로 인위적으로 건 것. 실제 인터넷 회선(손실·변동)과는 다르므로 실제 서버에서 재확인.

## 시험 환경 메모

- 두 컨테이너가 **같은 호스트 키**를 쓴다(이미지 빌드 때 키가 만들어져 공유됨). 호스트 키 바뀜 경고(AC-6)를 시험할 땐 컨테이너 시작 시 키를 새로 만들도록 바꿔야 한다.
- 시험용 비밀번호·키는 `spike/docker`에만 있고 키 파일은 git 제외(`spike/.gitignore`).

## 실제 서버 시험 (작가 환경, 2026-11-01)

구성: `<bastion>`(공인 IP, 22) → `<내부IP>:22`. 작가가 평소 `ssh -L 2222:<내부IP>:22` + FileZilla(`localhost:2222`, SFTP)로 쓰던 경로. 주소·계정은 공개 저장소라 기록하지 않음.

| 단계 | 결과 |
|---|---|
| bastion 접속·비밀번호 인증 | ✅ |
| bastion 호스트 키 ↔ `~/.ssh/known_hosts` | ✅ 일치 |
| bastion 위 direct-tcpip → 내부 서버 SSH 세션 | ✅ 로컬 포트 없음, 준비 0.5~0.8초 |
| 내부 서버 인증 / 두 번째 내부 연결 | ✅ / ✅ |
| 내부 서버 SFTP | ❌ subsystem 수락 직후 exit status 1, 0바이트 |
| 진단(exec) 출력 | `WARNING: Your password has expired.` / `Password change required but no TTY available.` |

**원인**: 내부 서버 계정의 비밀번호가 만료됨. OpenSSH(PAM)는 인증은 통과시킨 뒤 세션에서 비밀번호 변경을 요구하는데, SFTP·exec처럼 TTY가 없는 세션은 변경 창을 띄울 수 없어 바로 종료한다. FileZilla로 되던 시점엔 만료 전이었던 것. **russh 문제가 아니다.**

**앱 설계에 반영할 교훈**
1. russh `request_subsystem(true, …)`은 요청만 보내고 서버 응답을 기다리지 않는다 → 앱은 `Success/Failure`를 직접 기다리고, 실패·조기 종료 시 **stderr와 exit status를 반드시 수집**해 사용자에게 보여줘야 한다(그러지 않으면 "sender dropped" 같은 무의미한 오류만 남음).
2. **비밀번호 만료**를 별도 상태로 인식해 안내하고, 해당 서버의 **터미널 탭(PTY)** 에서 변경하도록 연결한다 → 기획서 FR-03b.
3. 시험한 두 서버(bastion·내부)의 호스트 키가 같다 — 복제 VM 또는 동일 기계로 추정. 앱 문제는 아니지만 호스트 키 기반 서버 구분이 약해짐.

**다음**: 내부 서버 비밀번호 변경(TTY가 있는 `ssh -t -J …` 로그인에서 변경 프롬프트) → `--single` · 기본 · 100MB 처리량 재시험.
