# 스파이크 — Swift ↔ Rust 핵심 연결(UniFFI) · SwiftTerm (2026-11-01)

> 기획서 §13 0단계 ④⑤. 코드: `spike/core-ffi`(Rust 핵심), `spike/swift-host`(Swift), `spike/term-host`(SwiftTerm).
> uniffi 0.32.2 · russh 0.65.0 · Swift 6.4.2 · SwiftTerm 1.99.2 · 시험 서버는 `spike/docker`.

## 결론

**N2 구조(Rust 핵심 + Swift 화면)가 성립한다.** jena-note와 같은 방식(Rust staticlib → `.xcframework` → SwiftPM `binaryTarget`)으로 붙었고, 앱에 필요한 세 가지 호출 형태가 모두 동작했다.

## 확인한 것

| 항목 | 결과 | 비고 |
|---|---|---|
| Swift `async/await` → Rust 비동기 함수 | ✅ | `#[uniffi::export(async_runtime = "tokio")]`. `connect`·`home`·`list`·`run` |
| `async let`으로 SFTP 목록 + 셸 명령 동시 호출 | ✅ | 한 SSH 세션 위 두 채널 |
| Rust 오류 → Swift `throws` (구간 구분) | ✅ | `Auth(hop: "bastion")`, `Auth(hop: "target")`, `Connect(hop, message)`, `HostKeyRejected(hop)` — 상태 로그에 "어느 쪽이 실패했는지" 그대로 쓸 수 있음(AC-4, FR-03a) |
| Rust → Swift 콜백(이벤트) | ✅ | `#[uniffi::export(foreign)] trait EventListener` — 상태 로그, 호스트 키 확인 |
| 호스트 키 판단을 Swift가 내림 | ✅ | Swift가 `false`를 돌려주면 접속 중단 → `HostKeyRejected`. 실제 앱의 확인 창(AC-6)이 들어갈 자리 |
| bastion 경유 접속을 Swift에서 | ✅ | `connect(target, via: bastion, listener)` 한 번 |
| 빌드 | ✅ | `core-ffi/build.sh` 한 번으로 재현. `MACOSX_DEPLOYMENT_TARGET=13.0` 필요(없으면 링크 경고) |
| 크기 | 5.2 MB (strip 4.2 MB) | 시험 실행 파일 전체 |

## 앱 설계에 반영할 것

1. **콜백은 백그라운드 스레드에서 온다**(tokio 스레드). Swift 화면 갱신은 반드시 메인 스레드로 넘겨야 함 → 핵심 이벤트를 받는 Swift 쪽 어댑터 하나(`@MainActor`로 전달)를 둔다.
2. **호스트 키 확인 콜백은 동기 `Bool` 반환**이라 사용자의 확인 창 응답을 기다리는 동안 그 연결의 작업 스레드가 묶인다. 연결이 3개뿐이라 당장 문제는 아니지만, 실제 앱에서는 "일단 거절 → 사용자가 허용하면 재접속" 또는 비동기 foreign trait로 바꾸는 걸 기술 설계에서 정한다.
3. 생성된 Swift 바인딩은 빌드 산출물로 다루고(커밋 여부는 기술 설계에서), Rust 쪽 공개 API가 곧 앱의 경계가 된다.

## ⚠️ 정정 — russh의 암호 라이브러리

기획서 §11.1에서 "russh는 순수 Rust 암호 → mac·Windows 빌드가 단순"이라고 적었는데 **틀렸다.** russh 0.65의 기본 암호 백엔드는 **aws-lc-rs(C·어셈블리 기반 aws-lc-sys)** 다(빌드 중 C 오브젝트 확인, `cargo tree -i aws-lc-sys`). 대안으로 `ring` 기능도 있으나 이것도 C·어셈블리를 포함한다.
- macOS: 별도 준비 없이 빌드됨(이번 스파이크).
- Windows: aws-lc-sys 빌드에 필요한 도구(CMake 등)가 있는지 **Windows 착수 전에 확인**. 막히면 `ring` 백엔드로 전환 검토.
- russh 선택 자체는 유지(구조상 이점은 그대로). "빌드 단순" 근거만 철회.

## SwiftTerm 한글 입력

`spike/term-host` — 로컬 zsh를 띄우는 SwiftTerm 창. 작가 직접 입력 결과(1차):

| 항목 | 결과 |
|---|---|
| 첫 한글 입력 | ❌ → ✅ 1차: 처음 입력한 한글이 자모로 낱낱이 들어감 → **2차(포커스 순서 수정 + `.app` 번들): 첫 입력부터 정상 조합** |
| 조합 중 커서 | ⚠️ 조합하는 동안 커서가 안 보임. **조합이 끝나면(스페이스 등) 다시 나타남** — 기능 문제 아닌 표시 문제 |
| Backspace | ✅ 조합 중 자모 단위, 완성 글자는 한 번에 (macOS 터미널 표준 동작) |
| `echo 한글` | ✅ |
| vim 한글 저장 → `cat` | ✅ |
| 한/영 전환 직후 영문 | ✅ |

**원인 분석**
- 커서: SwiftTerm은 조합 중인 글자를 커서 칸 위에 **불투명 배경의 미리보기 창(overlay)** 으로 덮어 그린다(`MacTerminalView.updateMarkedTextOverlay`, 다른 모든 하위 뷰 위에 추가). 그래서 커서가 가려진다. 라이브러리 내부(private) 동작이라 앱 쪽 설정으로는 못 바꿈 → **SwiftTerm 수정 필요**(MIT라 포크 가능, 원 저장소에 PR도 가능).
- 첫 입력: 창을 띄우는 순서(앱 활성화 전에 터미널에 포커스) 또는 `.app` 번들이 아닌 맨 실행 파일로 띄운 탓일 가능성. 2차 시험: 활성화 → 창 키 → 다음 실행 주기에 포커스 + 입력 문맥 활성화로 순서를 바꾸고, `.app` 번들로 감싸서 재시험.
실제 앱의 SSH 터미널은 로컬 프로세스 대신 russh 채널이 `TerminalView`에 데이터를 넣지만, 한글 입력 처리(IME)는 같은 뷰에 있으므로 이 시험으로 판단 가능하다.

**확정 (2차 시험 후)**
- 첫 입력: 앱 활성화 → 창 키 → 다음 실행 주기에 터미널 포커스 + `inputContext.activate()` 순서, 그리고 `.app` 번들 실행으로 해결. 실제 앱은 둘 다 기본으로 따른다(어느 쪽이 결정적이었는지는 가르지 않음 — 둘 다 원래 해야 할 일).
- 조합 중 커서: SwiftTerm 수정으로 해결 예정(MVP 1차 터미널 작업 때). 방향: 조합 글자를 커서 칸에 밑줄/반전으로 표시하고 커서를 그 뒤에 그림. MIT라 포크해서 고치고 원 저장소에 PR.

**스파이크 단계 종료(2026-11-01)**: russh·UniFFI·SwiftTerm 모두 "막는 문제 없음". 남은 것 = 실제 내부 서버 SFTP·처리량(고객사 비밀번호 변경 대기), Windows 빌드 도구·터미널(Windows 착수 전).
